1. Create Application Stacks with Podman Compose

Podman Compose is a compatibility layer for Docker Compose that works with Podman:

# Example docker-compose.yaml
version: '3'
services:
  web:
    image: nginx:latest
    ports:
      - "8080:80"
    depends_on:
      - app
    networks:
      - app-network
  app:
    image: myapp:latest
    environment:
      - DATABASE_HOST=db
    networks:
      - app-network
  db:
    image: postgres:15
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - app-network

volumes:
  db-data:

networks:
  app-network:
# Start the stack
podman compose up -d

# Stop the stack
podman compose down

# View status
podman compose ps

# View logs
podman compose logs -f

2. Understand Container Dependencies

Containers can depend on other containers for proper startup ordering:

# Start a database container first
podman run -d --name mydb -e POSTGRES_PASSWORD=secret postgres

# Start an application container that depends on the database
podman run -d -p 8080:80 --name myapp --link mydb:db myapp

Networking between containers:

  • Default network: Containers on the same pod can communicate via localhost
  • Custom networks: Create a shared network for containers to communicate by name
  • Podman pods: Containers in the same pod share network namespace
# Create a custom network
podman network create app-net

# Start containers on the same network
podman run -d --name db --network app-net -e POSTGRES_PASSWORD=secret postgres
podman run -d --name app --network app-net -p 8080:80 myapp

# Containers can now resolve each other by name
# The app container can reach db at hostname: db

3. Working with Environment Variables

# Set environment variables in docker-compose.yaml
environment:
  - APP_ENV=production
  - DATABASE_URL=postgres://db:5432/mydb

# Using a .env file (podman-compose supports this)
APP_ENV=production
DATABASE_URL=postgres://db:5432/mydb

# Override at runtime
podman compose up -d --env APP_ENV=staging

Service discovery: Containers on the same network can resolve other containers by their container name or service name in the compose file.

4. Working with Secrets

Podman supports secrets for managing sensitive data:

# Create a secret from a file
echo "mysecretpassword" | podman secret create mydb-pass -

# Run a container with the secret
podman run -d --name myapp --secret mydb-pass myimage

# Access the secret inside the container
cat /run/secrets/mydb-pass

# List secrets
podman secret ls

# Remove a secret
podman secret rm mydb-pass

Secrets in compose:

version: '3'
services:
  app:
    image: myapp
    secrets:
      - mydb-pass
      - api-key

secrets:
  mydb-pass:
    file: ./secrets/db-pass.txt
  api-key:
    external: true

5. Working with Volumes

# Named volumes in compose
volumes:
  db-data:
  app-cache:

# Bind mounts in compose
volumes:
  - ./data:/var/lib/data:Z
  - ./config:/etc/app/config:ro

Volume management:

  • Named volumes: Managed by Podman, stored in /var/lib/containers/storage
  • Bind mounts: Mount a specific host path into the container
  • Read-only: Add :ro to prevent writes
  • SELinux: Use :Z for private or :z for shared labels

6. Working with Configuration

# Using configuration files
# docker-compose.yaml
version: '3'
services:
  web:
    image: nginx
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro

# Or using ConfigMaps-like approach
# Copy config into the image during build
COPY config/app.conf /etc/app/app.conf

Configuration best practices:

  • Use environment variables for runtime configuration
  • Use volumes to mount configuration files
  • Keep configuration separate from application code
  • Use :ro (read-only) for configuration mounts to prevent accidental modifications
