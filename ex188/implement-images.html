Study Points for the Exam

1. Base Images — FROM Instruction

Specifies the base image for subsequent instructions. A valid Containerfile must have either ARG or FROM as its first instruction.

FROM registry.access.redhat.com/ubi9/ubi:latest
FROM registry.access.redhat.com/ubi9/ubi:9.4
FROM quay.io/redhat-isos-bootc/f4-bootc@sha256:abc123
  • If no tag is given, latest is applied automatically
  • FROM may appear multiple times to create multi-stage builds
  • Names can be assigned to build stages using AS <name>

2. Adding Content — RUN, ADD, COPY Instructions

RUN executes commands in a new layer and commits the results:

# Shell form (runs in /bin/sh -c)
RUN yum install -y httpd && yum clean all

# Executable form (preferred, avoids shell string munging)
RUN ["yum", "install", "-y", "httpd"]

COPY copies files from the build context into the container:

COPY index.html /var/www/html/
COPY ["src/", "/opt/app/"]

ADD is similar to COPY but can also unpack tarballs and fetch URLs:

ADD archive.tar.gz /opt/
ADD https://example.com/file.txt /opt/

COPY vs ADD: Prefer COPY for local files. Use ADD only when you need tar auto-extraction or URL fetching.

3. Runtime Environment — USER, WORKDIR, ENV, ARG

USER sets the username or UID to run the container as:

RUN groupadd -r myapp && useradd -r -g myapp myapp
USER myapp

WORKDIR sets the working directory for subsequent instructions:

WORKDIR /opt/app
COPY . .
RUN make
CMD ["./app"]

ENV sets environment variables that persist when the container runs:

ENV APP_HOME=/opt/app
ENV APP_ENV=production

ARG defines build-time arguments (not persisted in the final image):

ARG BUILD_VERSION=1.0
RUN echo "Building version $BUILD_VERSION"

4. Exposing Ports — EXPOSE Instruction

Documents which ports the container listens on at runtime. Does not actually publish the ports — use podman run -p to map them:

EXPOSE 80
EXPOSE 8080 8443

5. Specifying Commands — CMD and ENTRYPOINT

CMD provides default arguments for an executing container. Only the last CMD takes effect:

# Executable form (preferred)
CMD ["/usr/local/bin/app", "--config", "/etc/app.conf"]

# Shell form
CMD echo "Container started"

# Provide defaults to ENTRYPOINT
ENTRYPOINT ["/usr/local/bin/app"]
CMD ["--config", "/etc/app.conf"]

ENTRYPOINT sets the main command for the container. Arguments from CMD are passed as defaults, but can be overridden at runtime with podman run arguments.

CMD vs ENTRYPOINT:

  • CMD is overridden by any arguments passed to podman run
  • ENTRYPOINT persists; CMD arguments are appended and can be replaced
  • Use ENTRYPOINT + CMD for a fixed executable with configurable arguments

6. Container Volumes

Mount host directories into the container for persistent data:

# Bind mount (at runtime)
podman run -v /host/data:/container/data:Z myimage

# Named volume
podman run -v myvolume:/container/data myimage

SELinux relabeling: Use :Z for private labels (only this container can use the mount) or :z for shared labels (multiple containers can use the mount).

7. Security and Permissions

  • Rootless containers: Podman runs containers as the current user by default, not as root
  • USER instruction: Switch to a non-root user inside the container
  • SELinux: Labels must be properly set on bind-mounted content, or SELinux may prevent access
  • Network access: Containers are isolated by default; use --network or --privileged to modify

8. Container and Image Lifecycle

  • Build: podman build -t myimage:tag .
  • List images: podman images
  • Inspect: podman inspect myimage
  • Run: podman run -d -p 8080:80 myimage
  • List containers: podman ps
  • Stop: podman stop <container>
  • Remove: podman rm <container>
  • Prune images: podman image prune
  • Save/Load: podman save -o myimage.tar myimage and podman load -i myimage.tar
