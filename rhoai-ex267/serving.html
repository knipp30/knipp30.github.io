Model Serving

Deploy models with KServe — Standard and Advanced modes, OpenVINO, vLLM

Model Serving Workflow

RHOAI uses KServe (formerly KFServing) for model serving on the single-model serving platform. The workflow is:

  1. Store the model (S3 bucket, OCI container, or PVC)
  2. Deploy the model as an InferenceService
  3. Serve via the KServe endpoint (REST or gRPC)
  4. Monitor the deployed model

Two deployment modes:

  • Knative Serverless — Default, uses OpenShift Serverless; auto-scales to zero when idle
  • KServe RawDeployment — Standard Deployment resources; no serverless dependencies; always-on

KServe Architecture

KServe uses a two-plane architecture:

  • Control Plane — Configures and manages ModelServer pods (InferenceService CRD)
  • Data Plane — ModelServer pods serve the model with Knative for auto-scaling (Serverless mode)

Required dependencies for Knative Serverless:

  • Red Hat OpenShift Serverless Operator
  • Red Hat OpenShift Service Mesh
  • Authorino (optional, for token authentication with external routes)

Multi-model serving platform (ModelMesh) is also available for deploying many small models on a single runtime server.

Standard Deployment

Through the UI:

  • Open Data Science Project → Models tab → Deploy Model
  • Select storage type: PVC, S3, or Model Registry
  • Specify model path (e.g., /data/model/ or s3://bucket/path)
  • Select a ServingRuntime (runtime type)
  • Configure resources (CPU, memory, accelerators)
  • Set deployment mode (Serverless or RawDeployment)

Standard deployment via CLI:

# Create an InferenceService from PVC
oc apply -f - <<EOF
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: fraud-detection
  namespace: <project>
spec:
  predictor:
    model:
      modelFormat:
        name: onnx
        version: "1.0.0"
      runtime: vllm-runtime
      storage:
        key: my-s3-connection
        path: models/fraud-detection/
EOF

Advanced Deployment

Advanced deployment allows more granular control:

  • Custom ServingRuntime configuration
  • Multiple model formats (ONNX, PyTorch, TensorFlow, etc.)
  • Custom environment variables
  • Resource overrides
  • Custom CA bundles for TLS

OpenVINO Runtime

For CPU-optimized inference with Intel hardware:

# OpenVINO ServingRuntime
apiVersion: serving.kserve.io/v1alpha1
kind: ServingRuntime
metadata:
  name: openvino-pipeline
spec:
  supportedModelFormats:
    - name: openvino
      version: "2022.2"
  containers:
    - name: openvino-pipeline
      image: quay.io/modh/openvino:latest

vLLM Runtime for LLMs

vLLM is optimized for serving large language models with PagedAttention:

vLLM ServingRuntime for LLM deployment
apiVersion: serving.kserve.io/v1alpha1
kind: ServingRuntime
metadata:
  name: llm-vllm
spec:
  containers:
    - name: vllm
      image: quay.io/modh/vllm@sha256:...
  supportedModelFormats:
    - name: huggingface

Configure model-specific parameters like max_model_len, gpu_memory_utilization, max_num_seqs.
