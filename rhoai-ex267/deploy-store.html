Deploy & Store Models

Storage locations, deployment settings, serving configuration summary

Model Deployment Options

RHOAI supports two primary deployment modes:

Standard Mode

Simple deployment through the RHOAI dashboard UI:

  • Select a model from storage (PVC, S3, Registry)
  • Choose a serving runtime
  • Configure resources (CPU, memory, GPU)
  • Deploy with default settings

Advanced Mode

Granular control over deployment configuration:

  • Custom ServingRuntime definitions
  • Custom environment variables and secrets
  • Resource requests/limits overrides
  • Custom TLS/certificates
  • Advanced KServe configuration
  • Canary deployments and traffic splitting

Model Storage Types

Persistent Volume Claims (PVC)

Models stored in cluster storage, accessible at /opt/app-root/src/ in the workbench:

# Upload models to PVC in the IDE File Browser
# Navigate to /opt/app-root/src/ and upload model files

# Deploy from PVC via InferenceService
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
spec:
  predictor:
    model:
      runtime: <serving-runtime-name>
      storage:
        key: <pvc-connection-name>
        path: models/my-model/

S3 Buckets

External object storage for models:

spec:
  predictor:
    storageUri: s3://<bucket-name>/models/my-model
    # Or use a connection:
    # Storage is automatically mounted as environment variables

OCI Containers

Models packaged as OCI images (modelcars) for portability. Deployed using the Podman tool:

# Build OCI model image
podman build --format=oci -t quay.io/myorg/my-model:v1 .
podman push quay.io/myorg/my-model:v1

# Containerfile example
FROM registry.access.redhat.com/ubi9/ubi-micro:latest
COPY --chown=0:0 models /models
RUN chmod -R a=rX /models
USER 65534

# Deploy from OCI image via InferenceService
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
spec:
  predictor:
    model:
      runtime: <serving-runtime-name>
      storage:
        key: <oci-connection>
        path: models/my-model/

Configuring Deployment Settings

Key configuration options:

  • Replicas — Number of serving pods (scale based on load)
  • Resource requests — CPU and memory minimum
  • Resource limits — CPU and memory maximum
  • Accelerators — GPU allocation (nvidia.com/gpu count)
  • Timeout — Model load timeout
  • Canary weight — Traffic split for A/B testing
  • Ingress — Route configuration (domain, TLS)

Deployment Summary

The full deployment lifecycle:

  1. Train the model in a workbench
  2. Save the model to a storage location
  3. Register (optional) in the Model Registry
  4. Deploy as an InferenceService (Standard or Advanced)
  5. Monitor with TrustyAI (bias/drift) and KServe metrics
  6. Iterate — Retrain and redeploy based on monitoring insights
